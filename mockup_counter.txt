GLOBAL RULES (every embed obeys these)
────────────────────────────────────────────────────────────────────────
• Color accents (Discord) — set per embed variant:
    ACTIVE   #2B2D31 (embed bg)  success #57F287 (green)
    RUIN/ERR #ED4245 (red)       info    #5865F2 (blurple)
    milestone #FFD700 (gold)      neutral #2B2D31 (dark)
• Every embed: title starts with an emoji, ends with a footer
  "Peace✘ Counter · <relative timestamp>".
• Members always <@id> mentions (never raw IDs) — uncached members are
  fetched via members.fetch() before display.
• Every command defers then edits → no freezes.
• Buttons customId: counter:<area>:<action>:<ctx>
  (e.g. counter:panel:enable, counter:channel:reset:<gid>:<chid>)
• SelectMenus customId: counter:<area>:select:<ctx>
• ChannelSelectMenu customId: counter:<area>:channel:<ctx>
• Modals customId: counter:<area>:modal:<ctx>
• EVERY panel/confirm interaction reply is EPHEMERAL (only the invoker
  sees it). The ONLY visible messages are the ✅/❌ success & RUIN posts
  the bot slams into the counting channel itself.

─── EMOJI RULES (identical policy to VC/ToD modules) ───────────────
• Never hardcode emojis in commands — always import from emojis.js
  (src/utils/counter/emojis.js). Custom emoji IDs come from the central
  emojis registry (src/utils/shared/emojis.js) reusing the VC/ToD set
  where semantics overlap (correct ✅ / wrong ❌ / resets / history /
  check / refresh). No invented IDs, no new uploads.
• React/UI build uses the bot's stored customs whenever a default
  glyph has an equivalent; pure-Unicode defaults stay spelled out so
  review sees the exact glyph.

═══════════════════════════════════════════════════════════════════════
  Shown via StringSelectMenu 'counter:panel:config'. 5 rows of String
  SelectMenus, one per config key (Discord caps 5 rows/message):
  Row 1: 'counter:config:select:mode'   plh "Mode: Numbers only ▼"
         [Numbers only] [Numbers and arithmetic]
  Row 2: 'counter:config:select:on_ruin' plh "On Ruin: Delete message ▼"
         [Delete message] [Leave with ❌ reaction]
  Row 3: 'counter:config:select:on_success' plh "On Success: ✅ + prev ▼"
         [✅ + prev number] [✅ only] [nothing]
  Row 4: 'counter:config:select:behavior'
         plh "Same-user guard: ON · notify prev: ON · reset: to zero"
         [Same-user guard ON/OFF]
  Row 5: 'counter:config:select:milestone' plh "Milestones: every 100 ▼"
         [every 100] [every 500] [never]

  A milestone-save on reset works like this (matches the reference
  screenshot behavior):
    - reset_behavior 'to_checkpoint' → RUIN resets the counter to the
      last saved checkpoint (1..checkpoint_every) instead of 0.
    - checkpoint saved after every "checkpoint_every" correct counts.

 4. SUCCESS (public — posted in the counting channel)
═══════════════════════════════════════════════════════════════════════
  NOT an embed. On a correct count the bot only:
    - reacts to the message with ✅ then with the <:prev_number>
      unicoded number-reaction (see reactions contract below).
  No message is posted for a plain success.

  REACTIONS CONTRACT
  ──────────────────
  On correct count (message kept):
    ✅ reaction first, then the previous number as the next reaction
    (i.e. message "49" gets ✅ then 4️⃣8️⃣ so the counter reads easily).
  On RUIN (message deleted):
    if on_ruin = 'delete' → DELETE the offending message, no reaction.
    if on_ruin = 'react'  → leave the message, add ❌ reaction.
  RUIN message posted by bot ALWAYS visible in the channel (never
  ephemeral).

 SCHEMA (schema.sql — executed by db.js on boot, keep idempotent)
═══════════════════════════════════════════════════════════════════════
CREATE TABLE IF NOT EXISTS counter_channels (
  channel_id TEXT PRIMARY KEY,
  guild_id   TEXT NOT NULL,
  mode       TEXT NOT NULL DEFAULT 'numbers_only',
    -- 'numbers_only' | 'numbers_arithmetic'
  on_ruin    TEXT NOT NULL DEFAULT 'delete',
    -- 'delete' | 'react'
  on_success TEXT NOT NULL DEFAULT 'react_number',
    -- 'react_number' | 'react_check' | 'none'
  same_user_guard INTEGER NOT NULL DEFAULT 1,
  notify_previous INTEGER NOT NULL DEFAULT 1,
  reset_behavior TEXT NOT NULL DEFAULT 'to_zero',
    -- 'to_zero' | 'to_checkpoint'
  checkpoint_every INTEGER NOT NULL DEFAULT 100,
    -- 100 | 500 | 0 (0 = never)
  current   INTEGER NOT NULL DEFAULT 0,
  last_counter_id TEXT,
  best      INTEGER NOT NULL DEFAULT 0,
  resets    INTEGER NOT NULL DEFAULT 0,
  paused    INTEGER NOT NULL DEFAULT 0,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_counter_guild ON counter_channels(guild_id);

CREATE TABLE IF NOT EXISTS counter_history (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  channel_id TEXT NOT NULL,
  guild_id   TEXT NOT NULL,
  user_id    TEXT NOT NULL,
  number     INTEGER,            -- 0 on reset rows
  kind       TEXT NOT NULL,      -- 'count' | 'ruin' | 'reset'
  reason     TEXT,               -- 'wrong_number' | 'same_user_twice'
                                --  | 'invalid_format' | 'manual'
  ts         INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_counter_history_channel
  ON counter_history(channel_id, ts DESC-door);
CREATE INDEX IF NOT EXISTS idx_counter_history_user
  ON counter_history(guild_id, user_id, ts DESC);

CREATE TABLE IF NOT EXISTS counter_stats (
  channel_id TEXT PRIMARY KEY,
  best   INTEGER NOT NULL DEFAULT 0,
  counts INTEGER NOT NULL DEFAULT 0,
  ruins  INTEGER NOT NULL DEFAULT 0
);

─── CONCURRENCY & RACE SAFETY ────────────────────────────────────
Two members send the correct next number at the same instant. Only ONE
must win. Implementation:

  - Per-channel mutex: Map<channel_id, Promise> chain in game.js
  - Wrap the whole decision in db.transaction():
      const row = sqlChannelGet.get(channel_id);
      if (row.current + 1 !== computed) → return ruin
      if (row.last_counter_id === author) → return ruin
      updateChannel.run(...)
      insertHistory.run(...)
  - better-sqlite3 transactions are synchronous → inherently serialized
    across the Node process. Still chain a per-channel promise to guard
    against async work between read and write (e.g. an await fetch).
  - Test: fire 100 concurrent messageCreate events for the same channel
    with numbers 1..100 → exactly 100 successes, 0 ruins, current ===
    100.
